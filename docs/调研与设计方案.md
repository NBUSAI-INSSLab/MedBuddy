# 慢病管理平台 MedBuddy —— 调研与设计方案

> 版本 v1.0 ｜ 技术栈 Flask + Vue 3 + SQLite ｜ 文档日期 2026-10-19

---

## 一、方向调研

### 1.1 行业产品能力基线

对国内主流慢病管理信息化产品（中云慧通 AI 慢病管理系统、烽火信通全院慢病管理、健康界诊后管理平台、黑豹科技慢病平台等）的功能拆解，可归纳出**六条主线**：

| 主线 | 关键能力 | 本平台落地情况 |
|---|---|---|
| 患者全景档案 | 基础信息 + 病史 + 用药 + 检验 + 居家监测统一视图 | 患者详情页「全景档案」+ 指标时间序列 |
| 风险分层 | 多维度评分，自动识别高危/失访/控制不佳 | 规则+趋势的复合风险模型，红/橙/黄/绿四级 |
| 智能随访 | 按病种与风险自动排程、结构化记录 | 随访任务 + 计划生成（智能体产出，可采纳） |
| 远程监测与预警 | 血压/血糖/心电自动回传，异常触发预警 | 指标录入 + 阈值/趋势双通道预警引擎 |
| 个性化干预 | 饮食运动用药指导，随反馈动态调整 | 智能体基于画像+记忆+知识库生成 |
| 质控看板 | 达标率、随访完成率、管理人数 | 概览页 KPI + 病种达标率 + 风险分布 |

行业共识是「**风险驱动**」而非「台账填报」：把有限医护资源投向高危与失控人群。这直接决定了本平台的信息架构——概览页先呈现「需要我今天处理的人」，而不是数据总量。

### 1.2 智能体架构路线对比

| 路线 | 优点 | 风险 | 结论 |
|---|---|---|---|
| 单体 LLM 直接问答 | 实现最快 | 幻觉、无患者记忆、无指南依据，医疗场景不可接受 | 否决 |
| 全自主多智能体（AutoGen/LangGraph 多角色辩论） | 推理充分 | 链路长、成本高、行为不可预测，难以做确定性安全约束 | 仅借鉴「专科分工」思想 |
| **确定性流程 + LLM 生成（本方案）** | 安全边界可硬编码、可审计、可离线降级 | 灵活性略低 | **采用** |

参考 2026 年医疗智能体研究（Healink 出院随访框架、AVA 临床 RAG、Nirmitee 医疗记忆架构）的三条硬结论：

1. **物理约束优于提示词约束**：药物、过敏、危急值必须在代码层拦截，不能只写在 Prompt 里；
2. **三层记忆**：会话短期记忆（当前对话）/ 中期压缩记忆（历史摘要）/ 长期患者档案（结构化 + 事实记忆），跨会话保持；
3. **引用可溯源 + 低置信度拒答**：每条临床主张要能指回指南片段，检索分数不足时明确说"建议咨询医生"，而不是编造。

### 1.3 开源模型选型（在线 / 本地双通道）

| 模型 | 获取方式 | 特点 | 定位 |
|---|---|---|---|
| Qwen3-8B | 硅基流动 `api.siliconflow.cn/v1`（免费档） | 中文强、128K 上下文、OpenAI 兼容 | 默认在线模型 |
| DeepSeek-V3 / GLM-4-9B | 硅基流动 / 魔搭 `api-inference.modelscope.cn/v1` | 推理质量高 | 可选在线模型 |
| Qwen2.5-7B-Instruct | Ollama `127.0.0.1:11434/v1` | 完全本地、数据不出院 | 私有化部署 |
| 内置规则推理引擎 | 本平台自带 | 零依赖、零密钥、可解释 | 离线演示/降级兜底 |

因此 LLM 层做成**统一 OpenAI 兼容适配器 + 内置引擎兜底**：一套接口支持在线开源模型、本地 Ollama、任意兼容网关；未配置密钥时平台仍能完整演示（内置引擎基于患者数据与检索证据组装回答，不是随机文本）。

### 1.4 本地知识库技术选型

| 环节 | 方案 | 理由 |
|---|---|---|
| 解析 | TXT / Markdown / PDF（pypdf） | 覆盖指南、宣教材料 |
| 切分 | 标题感知 + 450 字窗口 + 80 字重叠 | 保留条目上下文，避免"断章取义" |
| 检索 | **BM25（jieba 分词）+ 字符 n-gram 向量余弦** 混合 | 纯本地、无需下载向量模型；医学术语精确匹配靠 BM25，表述差异靠向量 |
| 重排 | 病种匹配 / 文档权威度 / 标题命中 加权 | 同一问题优先返回本病种指南 |
| 可选增强 | 配置 OpenAI 兼容 `/embeddings`（如 bge-m3）后自动切换真向量 | 有 GPU/额度时可升级，接口不变 |
| 引用 | chunk → 文档标题 + 章节 + 片段 | 前端可展开查看原文 |

### 1.5 设计原则

1. 安全前置：红旗症状与危急值先于一切生成逻辑；
2. 证据优先：回答必须挂引用，检索不足则降级为建议就医；
3. 记忆可累积：每轮对话抽取事实/偏好/障碍写入长期记忆，下次自动注入；
4. 个性化可量化：用「个性化成熟度」把"越用越懂你"变成可见指标；
5. 数据不出域：知识库、患者数据、对话记录全部落本地 SQLite；
6. 主题可配置：CSS 变量驱动，5 套预设 + 自定义主色；
7. 全链路留痕：每次智能体调用记录注入上下文、命中片段、模型与耗时。

## 四、智能体设计

### 4.1 编排流水线（七步，确定性可审计）

| 步骤 | 输入 | 处理 | 输出 |
|---|---|---|---|
| ① 安全门禁 | 用户问题 + 最新指标 | 红旗症状词表、危急值阈值、自伤/急救识别 | 命中则走急救分支（不进入常规生成） |
| ② 上下文装配 | patient_id | 画像、在管慢病、在用药物、近 90 天指标、未处理预警、长期记忆 Top-8、历史摘要 | 紧凑上下文块（<1500 字） |
| ③ 检索 | 问题 + 病种标签 | 混合检索 Top-12 → 重排取 Top-4（阈值 0.18） | 证据片段 + 引用编号 |
| ④ Prompt 组装 | 上述全部 | 角色/边界/证据规则/回答结构 | messages |
| ⑤ 生成 | messages | LLM 流式；不可用则内置引擎 | token 流 |
| ⑥ 后置校验 | 回答 | 引用存在性、药物白名单、危急值复述、免责声明 | 修正后的回答 + 标记 |
| ⑦ 记忆/审计 | 对话 | 事实与偏好抽取入库，写调用日志 | 更新个性化成熟度 |

### 4.2 三层记忆

- **短期**：当前会话最近 8 条消息原文；
- **中期**：会话超过 8 条时，把更早消息压缩为「主诉/已给建议/待确认事项」摘要（规则抽取 + 可选 LLM 摘要）；
- **长期**：`memories` 表。每轮对话后抽取，例如"患者自述夜班后容易忘记晚上服药"→ `barrier`；"偏好低盐但抗拒水煮菜"→ `preference`；"希望三个月把 HbA1c 降到 7%"→ `goal`。带置信度与权重，检索时按 `weight × 时间衰减` 排序。

### 4.3 个性化机制

**个性化成熟度**（0–100，前端展示为环形进度，随使用上升）：

```
M = 30·min(1, 建档天数/90) + 25·min(1, 指标条数/60) + 15·min(1, 对话轮次/20)
  + 20·min(1, 记忆条数/12) + 10·min(1, 随访完成数/6)
```

分档：<35 起步期（以通用指南为主）｜35–65 成长期（开始引用个体趋势）｜>65 成熟期（可做个体化归因与方案微调）。

**回答个性化的四个落点**：① 用患者自己的数值与趋势说话；② 结合其用药与过敏做禁忌过滤；③ 结合记忆中的偏好/障碍给可执行建议；④ 检索时按病种过滤，避免跨病种泛化建议。

### 4.4 安全护栏

- 红旗症状：胸痛/胸闷压榨感、呼吸困难、意识模糊、单侧肢体无力、言语不清、收缩压 ≥180 或舒张压 ≥110、血糖 <3.9 或 >16.7、静息心率 >120、SpO₂ <90%、自伤言语 → 立即急救提示 + 医生介入标记；
- 药物：回答中出现的药名必须在患者用药清单内，否则标注"需医生评估"，不给出剂量；
- 边界：不诊断、不调药、不替代面诊；所有回答附免责声明；
- 溯源：有检索命中时必须引用；无命中时明确"知识库未覆盖"。

## 五、前端设计

- **布局**：左侧固定导航（宽度 232px）+ 顶栏 + 内容区，`height:100vh` 满窗，内容区独立滚动，任何分辨率不出现横向滚动；
- **主题**：`:root` CSS 变量（主色/主色浅/主色深/点缀色/阴影），5 套预设（橙色、橙蓝、蓝色、绿色、黑灰）+ 取色器自定义，localStorage + 后端用户偏好双写；
- **图表**：自研 SVG 组件（折线/面积、环形、柱状、迷你趋势），无 CDN 依赖，支持 hover 提示与参考区间带；
- **中文优先**：界面不出现英文副标题；医学缩写（HbA1c、SpO₂）保留并配中文注释；
- **AI 对话**：三栏（会话列表 / 消息流 / 证据与画像侧栏），流式打字，引用角标可点击展开原文；
- **饮食管理**：患者全景档案内独立标签页，含营养目标卡、分餐方案、食物宜忌、今日执行与近 14 天记录；
- **专家会诊**：患者端独立页面，先选专家/专家团再进入会诊室；会诊室为两栏（会诊对象与档案摘要 / 多专家消息流），专家发言带姓名、职称与专属头像色；
- **饮食拍照**：患者端「我的健康 · 今日饮食」按早餐/午餐/晚餐三个照片位记录，上传后本地完成色彩结构分析，估算热量与钠并给出改进建议；医生端档案内可查看照片与分析详情；
- **登录/注册**：分段式滑块切换（账号登录 / 用户注册），面板淡入淡出 + 输入图标、密码显隐、演示账号彩点，注册表单按「基本信息 / 账号设置 / 健康档案」分组。
- **导航**：医生端 3 项（首页概览、患者管理、智能助手）；患者端 2 项（我的健康、专家会诊）；管理员端 5 项（首页概览、医疗知识、用户管理、专家管理、平台配置）。系统面向社区医疗点：设备接入与饮食拍照归入患者自助，医疗知识与平台配置归管理员，用户管理仅管理员可见。
- **主题入口**：顶栏右上角常驻主题选择按钮，弹出 5 套预设色板与自定义主色，切换即生效并写回账号偏好（医生端不再需要平台配置页即可换肤）。
- **专家管理**：管理员端分「专家 / 专家团」两个选项卡，卡片展示知识库篇数、技能数、MCP 工具数与会诊次数；配置弹窗按「基本信息 / 人设 / 知识库绑定 / 技能 / 外部工具 / 上线状态」分组。

## 九、设备接入（MQTT 体征设备）

系统面向社区医疗点，患者端导航收敛为「我的健康 / 专家会诊」，不再单独开放设备页面：血压计、血氧仪、体温计与手环的数据由 MQTT 网关自动接入，按序列号绑定档案后参与趋势、预警与个性化成熟度计算；MQTT 网关开关、Broker 与主题在管理员「平台配置 · 设备接入」中维护；设备台账与原始报文接口（`/api/devices`）保留，供后续配发的患者自助接入页复用。

### 9.1 总体链路

```
血压计 / 血氧仪 / 体温计 / 手环
        │  MQTT 3.1.1（QoS 1）
        ▼
   Broker（Mosquitto / EMQX / amqtt，院内自建）
        │  topic: medbuddy/<device_sn>/vitals
        ▼
MedBuddy MQTT 网关（paho-mqtt，后台线程 + 自动重连）
        │  解析 → 量程校验 → 去重 → 入库 → 告警 → 日聚合 → 风险刷新
        ▼
metrics（source='device'）→ 达标率 / 风险分层 / 个性化成熟度 / 智能体上下文
```

网关与 Web 进程同源部署，配置保存在 `settings.mqtt_config`，修改后热重启，不影响其他请求。

### 9.2 报文协议

主题：`medbuddy/+/vitals`，第二段即设备序列号；报文内 `device_sn` 优先。

```json
{
  "device_sn": "MB-BP-1001",
  "patient_id": 1,
  "ts": "2026-10-19 08:30:00",
  "vitals": {"sbp": 135, "dbp": 85, "heart_rate": 76, "spo2": 98, "temp": 36.5, "hrv": 42},
  "battery": 86, "signal": -58
}
```

- 字段别名：`hr/pulse`、`SBP/DBP`、`spo/O2`、`temperature`、`rmssd/sdnn`，支持 `bp:{sbp,dbp}` 嵌套与扁平结构；
- CSV 兼容：`hr=76,sbp=135,dbp=85,spo2=98,temp=36.5,hrv=42`；
- 时间戳：秒/毫秒时间戳或常见日期格式，缺省取服务端时间；
- 未绑定设备可在报文携带 `patient_id` 自助绑定；关闭自动注册时，未登记设备直接拒收。

### 9.3 数据质量与安全

| 机制 | 说明 |
|---|---|
| 量程校验 | 收缩压 50–300、舒张压 20–200、心率 25–250、血氧 50–100、体温 30–45、HRV 1–400，越界丢弃并记录原因 |
| 边缘值标记 | 合理但偏离临床常见范围（如心率 <35）标 `quality=suspect` |
| 去重 | 同设备同指标 2 秒窗口（可配），并建部分唯一索引 `(device_sn, metric_type, measured_at)` |
| 告警去重 | 同类预警 30 分钟内不重复生成 |
| 未绑定隔离 | 数据写入 `device_readings` 留存，但不进入患者档案 |
| 权限 | 设备接入仅限患者本人（登记、绑定本人档案、测量、解绑）；MQTT 配置仅 admin/doctor |
| 审计 | 登记、绑定、配置修改、模拟上报全部写 `audit_log` |

### 9.4 数据库优化

1. **索引**：`metrics(patient_id, measured_at)`、`metrics(metric_type, measured_at)`、`metrics(source, measured_at)`、`device_readings(device_sn, received_at)`、`devices(patient_id)`；
2. **部分唯一索引**：仅对设备写入的指标去重，不影响手工与门诊数据；
3. **日聚合表** `metric_daily`：设备高频上报时，30/90 天趋势图与概览活跃度改读聚合表，单患者最多返回 120 个点；
4. **原始报文保留策略**：默认 30 天（可配），`prune_readings()` 定期清理，明细指标永久保留；
5. **批量提交**：一条报文的多项体征合并为一次 `executemany + commit`；
6. **风险刷新节流**：同一患者 45 秒内只重算一次风险分层，避免高频数据打满 CPU。

### 9.5 配置项（平台配置 · 设备接入）

`enabled`、`host`、`port`、`client_id`、`username`、`password`、`tls`、`qos`、`topic`、`payload_format`、`auto_register`、`dedupe_seconds`、`retention_days`。

提供「测试连接」（独立探针，不影响在线网关）、「保存并应用」（热重启）、「启动/停止网关」与运行状态（收报文数、入库指标数、错误数、最后报文时间、最近事件）。

### 9.6 验证方式（无硬件）

- 设备页「模拟上报」：按患者基线生成 6 组连续体征，走完整入库链路；
- `tools/mqtt_broker.py` 启动本地 Broker，配合任意 MQTT 客户端发布报文；
- `tests/test_mqtt.py`：16 项测试，含真实 Broker 端到端（订阅→入库→字段断言）。

## 十一、饮食管理（患者全景档案）

位置：患者全景档案 → 预警记录之后的「饮食管理」标签页。目标是把指南里的克数翻译成可执行的一日三餐，并用真实记录反向校正建议。

### 11.1 处方测算

- 标准体重 = 身高(cm) − 105；BMI 由身高体重计算。
- 能量：按 BMI 与年龄取 25–30 kcal/kg 标准体重；慢性肾脏病固定 30，慢阻肺 +2，肥胖 −2，70 岁以上 −2，按 50 kcal 取整。
- 蛋白质：一般 1.0 g/kg、糖尿病 1.1、慢阻肺 1.2、CKD 0.8；脂肪按 25% 能量；碳水由剩余能量反推。
- 钠：高血压 / 冠心病 / CKD 每日 1800 mg，其余 2000 mg；食盐按钠 ×2.54 换算，饮水 1500–1700 ml。
- 分餐：早餐 25%、午餐 35%、晚餐 30%、加餐 10%，每餐给出主食生重、蛋白份量、蔬菜份量与烹调油上限。

### 11.2 病种规则

| 病种 | 核心限制 | 配餐体现 |
|---|---|---|
| 高血压 | 钠 ≤1800 mg，警惕隐性盐 | 凉拌菜少盐、汤不放盐、限盐勺提示 |
| 2 型糖尿病 | 主食定量、低 GI、进餐顺序 | 杂粮饭 50–75 g 生重，先菜后饭 |
| 慢性肾脏病 | 蛋白 0.8 g/kg、限磷钾 | 低蛋白米/麦淀粉、蔬菜焯水、低钾水果 |
| 冠心病 / 血脂异常 | 限饱和脂肪与反式脂肪 | 清蒸鱼、瘦肉、烹调油 ≤25 g/日 |
| 慢阻肺 | 少量多餐、保证蛋白 | 加餐酸奶与全麦饼干，避免过饱 |

### 11.3 记录与执行度

`diet_logs` 保存日期、餐次、食物描述、热量与钠。未填数值时按食物关键词表（米饭、面条、腌制品、外卖等）自动估算，返回 `estimated=true` 提示为估算值。近 7 天执行分 = 记录天数（60）+ 平均能量在目标 ±20%（20）+ 平均钠不超目标（20），用于驱动页面圆环与后续建议。

### 11.4 拍照记录与本地视觉分析

患者每天可对餐盘拍照上传，平台在本地（Pillow，无需外部视觉模型）完成分析：

1. **背景分离**：以画面外圈颜色为桌面参考，结合"高亮低饱和 = 白瓷盘"与暗部阴影规则剔除盘面，白米饭因偏黄、饱和度略高得以保留；
2. **结构归类**：其余像素按 HSV 色相分为蔬菜 / 主食 / 优质蛋白 / 油脂酱汁四类，输出占比条；
3. **估算**：按占比 × 能量密度 × 铺满程度估算热量，按酱汁与蛋白占比估算钠；可附加文字描述做多源融合（视觉 60% + 文本 40%）；
4. **评估**：结构分 0–100（蔬菜、主食定量、蛋白、清淡四维）+ 分级（优秀/良好/一般/待改善）+ 逐项发现与下一步建议，并按病种（高血压限钠、糖尿病主食定量、肾病限蛋白）加码；
5. **留痕**：照片存 `data/uploads/diet/<pid>/`，分析 JSON 存 `diet_logs.analysis`，置信度与免责声明随结果返回。

接口：`POST /api/my/diet/photo`（患者本人）与 `POST /api/patients/<id>/diet/photo`（医生代录），照片经 `GET /api/patients/<id>/diet/photos/<name>` 鉴权读取。

### 11.5 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/patients/<id>/diet` | 处方 + 近 14 天记录 + 执行度摘要 |

| POST | `/api/patients/<id>/diet/logs` | 新增饮食记录，可自动估算热量与钠 |

### 12.2 会诊流程

```
选择专家/专家团 → 填写会诊主题（可跳过）
      ▼

      ▼
患者提问 → SSE 流式返回
      ├─ 单专家：一位数字人作答
      └─ 专家团：按成员顺序依次作答，后一位可看到前序意见摘要
      ▼
安全门禁命中 → 仅由首位专家输出急救指引，跳过常规会诊
      ▼
每条发言落库（speaker_id / speaker_name / meta），刷新会话时间
```

作答统一注入患者全景档案，并按当前专家绑定的知识库做证据检索（未绑定则用全库）；启用技能与已授权 MCP 工具写入系统提示词，每条发言的 `meta` 记录技能数、工具数与命中片段，患者端可查看。在线模型不可用时自动降级为专科规则引擎，保证演示与离线环境可用。所有回答附「不能替代线下面诊」声明，涉及调药一律转交签约医生。
